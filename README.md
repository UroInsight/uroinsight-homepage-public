# uroinsight-homepage
유로인사이트 홈페이지

## Git 규칙

### 작업 흐름

모든 작업은 GitHub Issue에서 시작합니다. 이슈를 만든 뒤 그 이슈 번호로 브랜치를 만들어 작업하고, 작업이 끝나면 PR을 올려 리뷰를 받은 다음 `main`에 머지합니다. `main`에 직접 커밋하지 않습니다.

### 브랜치 이름

브랜치 이름은 `타입/#이슈번호` 형태로 짓습니다. 브랜치만 봐도 어떤 작업인지 알 수 있도록 이슈 번호 뒤에 하이픈과 짧은 설명을 붙여도 됩니다. 설명은 영어 소문자로 쓰고, 단어 사이는 하이픈으로 잇습니다.

> 예시: `feat/#33-login-page`

타입은 작업의 성격에 따라 고릅니다.

| 타입 | 이런 작업일 때 |
|------|------|
| `feat` | 새로운 기능을 추가할 때 |
| `fix` | 버그를 고칠 때 |
| `refactor` | 동작은 그대로 두고 코드 구조만 바꿀 때 |
| `chore` | 빌드, 설정, 패키지, 로그처럼 기능과 직접 관련 없는 작업일 때 |
| `docs` | 문서만 수정할 때 |
| `test` | 테스트를 추가하거나 고칠 때 |

한 이슈 안에서 여러 종류의 작업을 했다면 가장 비중이 큰 작업의 타입을 씁니다. 한 이슈를 여러 브랜치로 나눠 작업할 때는 뒤에 붙인 설명으로 브랜치를 구분합니다.

### 커밋 메시지

커밋 메시지는 맨 앞에 대괄호로 이슈 번호를 적고, 그 뒤에 타입과 콜론, 그리고 무엇을 바꿨는지 한 줄로 적습니다. 타입은 브랜치와 같은 목록에서 고르되, 브랜치 타입과 달라도 괜찮습니다. 버그 수정 브랜치에서 코드 정리를 했다면 그 커밋은 `refactor`로 적습니다.

> 예시: `[#33] feat: 로그인 화면 추가`
